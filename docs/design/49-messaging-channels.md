# Text an agent from your phone

Design proposal, 6 November 2026; no implementation claim. Telegram first, using the owner's bot and account. Reuse design [48](48-external-agents.md)'s verified identities, ordinary inbox, notices, keyed receipts and revocation fences; its separately reviewed proposal must be composed before implementation. A channel transports Owner mail to an existing agent; it creates neither a second agent nor a second inbox. No hosted relay or required Photon service.

## Connect in the TUI or desktop

**Channels → Add → Telegram** selects project and agent by name. Link to BotFather with inline guidance, accept the owner's bot token once in a masked connection field, and put it straight into the native key store; test the token and show the verified bot name. Never use configuration files, environment variables, commands, ordinary chat or logs for credentials. An existing key-store connection skips token entry. A headless host receives the connection through Add machine's protected source flow, never manual file transfer.

After the token, **Connect phone** is one guided tap: open a one-use bot link/QR, handle the phone challenge internally, and show the provider account for Owner approval inline. Bind the bot account, numeric sender and private chat to that Owner and exact targets. Neither first contact nor possession of the link grants access. Both frontends share enrollment and lifecycle machinery; no typed IDs, ports, copied pairing codes or additional configuration steps.

Choose **Save only** (default), or authorize **Start/resume these agents when I confirm on my phone**, using their existing permission profiles and applicable cost limits. This is a proposed narrow lifecycle authorization, not an existing R0 Send permission or general remote control. Finish with an actual saved/read/reply round trip; display unsupported steps honestly. Disconnect revokes the binding and queued output; rotate the bot credential separately if compromised.

**Known setup cost:** bring-your-own Telegram accounts require this one protected bot-token entry. Telegram documents BotFather tokens, not general OAuth for existing bots. Managed-bot enrollment is a later option if it becomes usable without a preauthorized manager; it currently has that prerequisite. No shared management service is implied. [Telegram bot management](https://core.telegram.org/bots/features#botfather), [managed bots](https://core.telegram.org/bots/features#managed-bots).

## Say exactly what happened

One phone message gets a stable short receipt and a status card, updated where supported; otherwise send linked status messages. Status facts need not occur in this order. Avoid the ambiguous label “delivered.”

| Sender sees | Required fact |
| --- | --- |
| **Saved in Alex's inbox** | Authorized mail and its provider-event mapping committed durably; read the keyed receipt back. A socket write or Telegram tick is insufficient. |
| **Woke Alex / notice received** | The exact current provider conversation committed the correlated mail notice. Launch acceptance, a running PID, stdin success and vendor RPC acceptance alone do not qualify. An already working agent may need no new wake; a route without this proof shows **notice receipt unknown**, not woke. |
| **Read by Alex** | That recipient's exact message has a committed read marker. Listing headers, plugin notification and dismissing are distinct. This proves tool access, not understanding or task acceptance. |
| **Alex replied** | A verified reply referencing the original message committed to the same mail history. Show **reply waiting for Telegram**, **sent to Telegram**, or **send outcome unknown** separately; platform acceptance is not proof the human read it. |

Before a saved receipt, show failure or **save outcome unknown**, resolving with the original key rather than telling the sender to resend. After saving, wake/output failures retain the mail and show the reason. Never turn a timeout into success. Replies retain the registered agent identity; the adapter cannot compose agent replies. Task acceptance and completion remain separate explicit agent messages, as in 48.

| Agent condition | Behavior and phone choice |
| --- | --- |
| Stopped | **Saved; Alex is stopped and has not been notified.** Offer **Keep waiting** and **Start/resume**. A confirmed action uses only the exact preauthorized lifecycle binding above; otherwise request approval in TUI/desktop. Use the existing launch/resume coordinator, preserving conversation and sandbox. Failure leaves saved mail pending. No new session or permission widening by implication. |
| Busy | **Saved; waiting for Alex to read.** Autonomous Claude waits for idle; Codex uses its supported serialized input/steer path. Do not interrupt, restart or duplicate work. Show notice receipt only after its evidence exists. |
| Attended Claude | Use the provider-native plugin route; never synthesize console input. If the plugin/session cannot receive, show that reason and keep mail pending. |
| Never reads / never replies | After 60 seconds without a read marker show **Not read yet**, elapsed time and current reason; after reading show **Read; no reply yet**. Offer status, the authorized resume choice or another agent selected explicitly. No repeated wake loop, automatic rerouting, read marking or fabricated reply. |

On the inspected Rust base `a04c3ca6`, `process/mail.rs` skips inactive/unbound work, gates autonomous Claude on idle, and bypasses attended Claude for its plugin; provider input is correlated before delivery observation. `claude_harness/mail.rs` also refuses attended stdin offers. These are source findings, not native stopped-agent proof. Independent native qualification must establish actual send receipt, unread retention and resume behavior before implementation acceptance; this proposal does not claim mail currently starts stopped agents.

## Paired sender means Owner mail

Reuse 48's authenticated admission and verified-sender notice format. The host resolves the channel binding to `paired_owner`, recording provider provenance and exact scope; a display name, forwarded “Owner” text, chat membership or adapter-supplied actor cannot grant standing. Native agents obey that verified Owner mail under the sender ruling; quoted/replied-to text and attachments remain data, and permissions never expand. Start with private text chats only; reject groups, anonymous senders, edits-as-new-instructions and attachments explicitly.

Pair only an authenticated immutable provider subject and destination. Reject all unpaired traffic before inbox admission; rate-limit enrollment attempts. Recheck binding revision/scope on inbound admission, phone actions and outbound release; phone actions bind the sender, saved message, exact lifecycle/profile and expiring one-use action key. Revocation prevents queued private output reaching the old destination. A stolen paired account can issue Owner instructions within its grant and read channel replies; bot-token compromise can expose messages or impersonate the transport. Show that cost at consent, offer native revoke, and never treat this credential as machine/OS Owner authority. Telegram and the channel provider also see the transmitted content.

Email must additionally authenticate the sender. Pin a trusted receiving MTA's `authserv-id`, authenticate its connection, and require it to strip forged matching Authentication-Results before stamping its own result. Check aligned authentication and the exact paired address. Domain authentication alone does not prove the individual mailbox: require a trusted authenticated-mailbox assertion or enrolled message signature for Owner admission; otherwise email is notice-only. Missing/ambiguous proof refuses, with no trust-From opt-out. [Hermes email adapter](https://github.com/NousResearch/hermes-agent/blob/74915d7af8d3115c3eb821893f3c01ab783146a5/plugins/platforms/email/adapter.py), [RFC 8601 trust boundary](https://www.rfc-editor.org/rfc/rfc8601.html#section-7.1).

## One small adapter boundary

Adapters own authenticated connect/disconnect, provider event identity, receive/ack, text send/edit and typed failures/capabilities. The host owns authorization, target selection, durable deduplication, lifecycle, status projection and reply outbox. Normalize `{connection, verified subject, chat/thread, event/revision, reply-to, text}`; never accept an actor or arbitrary launch command from the platform. Provider IDs are scoped by connection generation. Bind conversation routing to stable agent identity; changed target/binding requires fresh approval.

Atomically save the accepted message, deduplication key and reply route before acknowledging provider input; denied input gets a bounded rejection disposition, never a saved receipt. Retries after a crash recover the same receipt. Drain a durable outbound queue with bounded backoff, provider rate limits and loop suppression; uncertain sends retain their outcome instead of promising exactly-once external delivery. Bound queues and text sizes; refuse overflow visibly rather than truncate. Keep receipts/status in the existing mail history.

Telegram uses outbound HTTPS long polling, one consumer per bot. Advance `getUpdates` offsets only after durable handling; preserve backlog on restart. Updates expire at the provider after at most 24 hours: a host outage may lose unsaved messages, so report possible gaps and never retrospectively claim saved/read. No inbound public endpoint is needed. [Telegram update contract](https://core.telegram.org/bots/api#getting-updates).

Slack, Discord, email and iMessage implement this same boundary, declaring their real identity, reply threading, edit, acknowledgement and reconnect capabilities. Qualify each separately. A user-operated BlueBubbles or Photon bridge may supply iMessage transport; its authenticated connection and sender proof still need qualification. Neither vendor is mandatory; bridge unavailability stays visible.

Borrow Hermes's normalized events, adapter capabilities, scoped access policy, reconnect/backoff, reply routing and duplicate/echo handling. Read its [platform guide](https://github.com/NousResearch/hermes-agent/blob/74915d7af8d3115c3eb821893f3c01ab783146a5/gateway/platforms/ADDING_A_PLATFORM.md), [base](https://github.com/NousResearch/hermes-agent/blob/74915d7af8d3115c3eb821893f3c01ab783146a5/gateway/platforms/base.py), [access policy](https://github.com/NousResearch/hermes-agent/blob/74915d7af8d3115c3eb821893f3c01ab783146a5/gateway/platforms/access_policy_mixin.py), and [Telegram adapter](https://github.com/NousResearch/hermes-agent/blob/74915d7af8d3115c3eb821893f3c01ab783146a5/plugins/platforms/telegram/adapter.py). Translate the useful patterns to Rust; do not adopt its configuration/env setup, optional open access, cold-start backlog dropping or best-effort receipt persistence. No Python runtime or copied code here. If implementation carries code/substantial portions, retain the upstream copyright and [MIT notice](https://github.com/NousResearch/hermes-agent/blob/74915d7af8d3115c3eb821893f3c01ab783146a5/LICENSE).

Acceptance needs real phone→inbox→agent work→verified reply in both frontends and Claude/Codex paths, including stopped/busy/attended/never-read agents, restart at save/ack boundaries, reply outage, duplicate updates, revocation, forged sender and oversized input. Credentials/handoffs and future providers remain unqualified until exercised. Design-only: no source changes, suites or land-preflight.
